52. 抓外站必须逐跳做 SSRF 校验,内网保护不许因为「页面自己跳过去」而放宽(P32,2026-11-16):东财这类站在防机器人时会 302 到 `127.0.0.1`,所以「初始 URL 安全」不等于「抓取安全」。规矩:唯一判定入口是新模块 `ttxt/crawler/url_safety.py`(`check_url` / `check_cached` / `walk`),拒绝 scheme 白名单外的地址、环回、私网、链路本地、组播、保留段、IPv6 本地与 ULA,外加 `0.0.0.0/8`、`198.18.0.0/15` 与文档段;`localhost` 与 `*.localhost` **按主机名直接拒绝,不许等 DNS 结果**;公网域名解析出私网 IP 同样拒;多级跳转**每一跳都重新解析、重新判定**,判定不过立即终止并记 `crawl.fetch.redirect_chain`。四条硬要求写死在代码里:`Fetcher.get(..., follow_redirects=False)` 必须显式关自动跳转、`fetch_page()` 的初始 URL 必须先过 `check_url`、`StealthySession.fetch()` 必须挂请求拦截器、robots 的 `urlopen` 必须换成「禁自动跳转 + `page.route("**/*")` 拦主文档、子资源、iframe、弹窗(同一个 context 全过),命中即 `abort("blockedbyclient")` 并记 `crawl.browser.blocked_by_ssrf_guard`;Playwright 官方说明 SW 发起的请求可能绕过 `route`,所以一旦出现 Service Worker 就 `context.on("serviceworker")` 立刻 `stop()`(context 用弱引用记账 —— 实测 `id()` 会在对象回收后复用同一数值,导致监听漏挂)。第二层是进程级 `--host-resolver-rules`,兜住拦截器之外的旁路。实测四个坑必须记住:①规则串里出现方括号(`MAP [::1] ~NOTFOUND`)是**非法语法,Chromium 200 并命中本机服务),这一条完全靠第一层拦截器和 SW 停用工兜住;又因为 `ProxyOverride` 含 `localhost;127.*;192.168.*;10.*;172.16.*`,内网目标根本不经代理直连,所以第一层才是主控。③有系统代理时 host-resolver-rules 对**经代理转发的公网主机不起作用**(解析交给代理),它只管直连主机 —— 53. 共用同一个浏览器 profile 的进程必须靠操作系统级的锁互斥,不许「启动失败就删锁文件」(P36,2026-11-17):Worker 与 `metrics_fetch` 是两个进程,共用同一份 `02_crawler/.browser/profile`,而 Chromium 同一时刻只允许一个进程持有 profile(实测:第二个进程 1.9 秒报 `TargetClosedError ... browser has been closed`)。规矩:①起浏览器只有一个入口 `fetcher.browser_session()`,它先取 `ttxt/crawler/browser_lock.py` 的锁再启动,同一进程内嵌套只起一个浏览器;②锁必须是内核事实,不是自制的账本:锁文件 `02_crawler/.browser/profile.lock` 放在 profile 目录**之外**(浏览器清 profile 清不掉它),Windows 用 `msvcrt.locking` 锁 1MB 偏移处的一个字节(POSIX 走 `fcntl.flock`,本机未实测),持锁进程一死(含 `taskkill /T /F` 强杀)句柄关闭、锁自动消失 ⇒ 不靠 PID 判活、不看时间戳、不做「陈旧锁清理」;③等不到锁必须给出明确状态,不许伪装成功:指标采集该类目不启动浏览器、不发请求,记 `skipped_browser_busy`并带上持锁者 pid/tag,本轮后续类目直接让路;Worker 侧任务保持 running 干等,锁放掉就继续;④等锁预算进配置:`browser.lock_wait_s`(600s)/`browser.lock_poll_s`(2s),单个任务可覆盖 `lock_wait_s`(metrics_fetch_6h=300s),且必须小于该任务的超时,别把等待变成永久挂起;⑤旧的 `_clear_profile_locks()`(启动失败就无条件删 `lockfile`/`Singleton*`)必须删除:先用内核的共享冲突证明「没有活进程持有」(`browser_lock.held_by_live_process`:PermissionError=有人正在用),证明不了就保留原样并记 error。实测依据:本机运行中的 Chromium profile 里只有 `lockfile` 一个锁文件且它被独占(连读都 PermissionError),`SingletonLock/SingletonCookie/SingletonSocket` 根本不存在 ⇒ 旧代码一直在删根本不存在的文件,还可能删掉别人正在用的锁。生产实测(2026-11-17 12:19–12:34,队列空闲、另一个真进程持锁):`metrics_fetch` 等满 300.0 秒 ⇒ `skipped_browser_busy`(5 个类目全部跳过、errors 为空),30 次采样 chrome 进程数恒为 0,profile 2221 个文件 / 662,727,551 字节与 mtime 前后完全一致(根本没启动浏览器);同一时段静态 HTTP 采集任务 8.03 秒跑完(不占这把锁);放锁后 Worker 那条已等 152.0 秒的浏览器任务立即起浏览器并 done(11 页、10 条入库);放锁前另跑一轮同一任务真实成功(218.2 秒、5 类目 ok)⇒ 互斥生效且正常路径没被破坏。红线:不许为了提高成功率而放宽锁;不许新增第二处起浏览器的代码;静态抓取不得触碰这把锁;改锁相关代码必须重启被托管的 scheduler/worker 才生效(`taskkill /T /F /PID <pid>`,supervisor 约 30 秒内用新代码重新拉起);验收测试必须用真 subprocess 多进程,不许拿 mock 冒充跨进程(21 条见 `10_tests/test_p36_browser_lock.py`),且如实写明:Windows 已实测,POSIX 分支未在本机验证。
